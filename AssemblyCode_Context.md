# AssemblyCode Plugin - Context & Decisions Log

## ИСТОРИЧЕСКИЙ КОНТЕКСТ ПРОЕКТА (Перенос логики из Dynamo)

Изначально логика плагина базировалась на громоздком Dynamo-скрипте. При портировании на C# были приняты следующие фундаментальные архитектурные решения:

### А. Архитектура обработки потоков и суффикс `_BGL`
**Суть:** В Dynamo надземные и подземные элементы обрабатывались как два абсолютно разных потока на основе заранее заданного параметра `FAM_Underground`.
**Решение в плагине:** Плагин читает параметр `FAM_Underground` (или аналогичный, настроенный пользователем) прямо из элемента. 
- Для **подземных** элементов (`FAM_Underground == "Подземная часть"`): если у типа нет суффикса `_BGL`, создается его дубликат с этим суффиксом.
- Для **надземных** элементов: если у типа ошибочно есть суффикс `_BGL`, создается дубликат без него.
- **Обоснование:** Такое поведение гарантирует строгое разделение спецификаций и объемов работ для надземной и подземной частей здания, что критично для BIM-стандартов.

### Б. Продвинутая рейтинговая система классификации (`ClassifierRatingEngine`)
**Суть:** Коды классификатора подбираются не простым совпадением, а через сложную систему весов (Bonuses/ExtraTrue) и списков включения/исключения (anyTrue, allTrue, exceptions).
**Решение в плагине:** Реализована иерархическая проверка: после нахождения подходящего кода (например, через ключевые слова), плагин проверяет родительский раздел кода. Подземные элементы обязаны находиться в разделе, название которого содержит слова вроде "подзем" или "ниже", а надземные — наоборот. Списки исключений строго разделены.
**Обоснование:** Обеспечивает максимальную точность назначения кодов, исключая ситуации, когда надземная стена получает код подземной гидроизоляции из-за совпадения одного слова в описании типа.

### В. Phantom Group Pipeline (Работа с элементами в группах)
**Суть:** Revit запрещает напрямую менять тип элемента, находящегося внутри группы (Group).
**Решение в плагине:** Реализован менеджер мутаций (`GroupMutationManager`). Изменения для сгруппированных элементов откладываются. Затем плагин временно исключает элементы из групп, применяет новый код/типоразмер, после чего корректно восстанавливает структуру групп.
**Обоснование:** Единственный способ программно обновить классификатор у сгруппированных элементов без "разрушения" модели.

## ТЕКУЩИЕ ИЗМЕНЕНИЯ И УЛУЧШЕНИЯ UI (Последние сессии)

## 1. Рефакторинг главного окна (MainWindow.xaml)
**Что сделано:** 
- Интерфейс настроек переведён в вертикальный вид (размещение блоков друг под другом).
- Переключатель «Не делить элементы на выше и ниже нуля» перемещен в самый верх.
- Опция «Не добавлять суффикс _BGL» перенесена в окно настроек Идентификатора зон (`UndergroundIdentificationDialog`).
- Кнопка вызова диалога "Идентификатор зоны" выровнена по ширине с блоком верхнего/нижнего нуля.

**Обоснование:** 
- Эти изменения улучшают визуальную компоновку, объединяют связанные опции в логические блоки и экономят полезное пространство окна. Логика суффиксов BGL тесно связана с распределением зон, поэтому её перенос в соответствующий диалог оправдан.

## 2. Фильтрация элементов без параметра "Assembly Code" (AssemblyCodeProcessor.cs)
**Что сделано:** 
- Добавлен метод `HasParameter` для проверки наличия целевого параметра классификатора (как у экземпляра, так и у типоразмера).
- Элементы, не имеющие этого параметра, отсекаются на самом раннем этапе (при сборе `FilteredElementCollector`).

**Обоснование:** 
- Элементы, которые физически не могут принять значение кода, не должны попадать в отчёт "Без кода", так как это загромождает таблицу и путает пользователя некорректной статистикой.

## 3. Фильтрация столбцов в окне отчёта (ReportWindow.xaml / .xaml.cs)
**Что сделано:** 
- В заголовки колонок таблиц `GridUnassigned`, `GridSpanning` и `GridGrouped` добавлена кнопка-воронка для вызова фильтров (аналог из `RevisionViewer`).
- При нажатии на воронку появляется Popup-меню (`FilterPopup`) с чекбоксами для каждого уникального значения в столбце.
- Активный фильтр подсвечивает воронку синим цветом.

**Обоснование:** 
- В отчёте могут быть сотни элементов разных категорий и типов. Локальная фильтрация в DataGrid сильно упрощает поиск нужных данных. Цветовая индикация предотвращает ситуации, когда пользователь "теряет" данные из-за забытого фильтра.

## 4. Запоминание состояния фильтров
**Что сделано:** 
- В интерфейс `ReportWindow` добавлен тумблер (CheckBox) "Запоминать состояние фильтров".
- Если опция включена, при закрытии окна список выключенных фильтров сериализуется и сохраняется в `%AppData%\Apex\AssemblyCodeReportFilters.txt`.
- При открытии отчёта настройки восстанавливаются.

**Обоснование:** 
- Экономия времени пользователя: если он занимается кодификацией определенной категории (например, скрыл все "Стены" и работает только с "Перекрытиями"), ему не придется заново настраивать фильтр при каждом перезапуске плагина.

## 5. Корректный сбор категорий Revit (RuleEditDialog.xaml.cs)
**Что сделано:** 
- Исправлена проблема отсутствия подкатегорий (например, `OST_EdgeSlab` - Края плит) в выпадающем списке категорий при настройке правила.
- Внедрён рекурсивный обход `cat.SubCategories` с жесткой проверкой на присутствие категории в перечислении `BuiltInCategory`.

**Обоснование:** 
- Свойство `doc.Settings.Categories` содержит только родительские/корневые категории. Однако пользователь может классифицировать и элементы подкатегорий. Фильтрация через `Enum.IsDefined(typeof(BuiltInCategory), id)` гарантирует, что мы добавляем системные подкатегории, но отсекаем пользовательский мусор (стили/веса линий, материалы), который сломал бы UI.

## 6. Игнорирование групп с 2D-элементами и групп без мутаций (AssemblyCodeProcessor.cs)
**Что сделано:** 
- В метод `ClusterizeGroupMutations` добавлена проверка наличия мутаций. Если для типа группы нет ни одной отложенной мутации, тип группы полностью пропускается.
- Также добавлена проверка наличия 2D-элементов (детализации, цветовых областей и т.д.) внутри обрабатываемых групп.
- Если хотя бы один элемент в группе имеет свойство `ViewSpecific == true`, вся группа пропускается с записью предупреждения в лог.

**Обоснование:** 
- Проверка на наличие мутаций избавляет Revit от необходимости создавать "фантомные" группы для всех типов групп в проекте (что занимало десятки секунд при большом количестве типов групп).
- Группы с элементами аннотаций/узлов вызывают системные исключения в Revit API (например: `Detail Filled Region can't be placed in 3D Views`), когда плагин пытается создать фантомную эталонную группу на 3D-виде для вычисления её угла поворота и трансформации. Такие группы ломают процесс и теперь безопасно пропускаются.
